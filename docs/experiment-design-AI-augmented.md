# Experiment Design

### X axis

Varying "maximum amount of rows per partition" from 2^1=2 to 2^18=262.144.
It will be a log scale, doubling for every run.

### Y axis

We will measure the time it takes to retrieve a single row based on a unique id on the row.
A measurement of the `durationMs` value.

### Procedure

We will use the exact same data for all runs. It will be 1M rows generated by a python script that uses a number generator that takes a seed (the seed will be 67). The columns of the data will be (id long, name string, random-number double). The id will be an increasing long from 1 to 1M. We will double the partition size for run/data point. 

We will run the engine by packaging the program with `mvn package`, then using the `./engine.sh` script to run the program with the test queries.

The query is `SELECT * FROM experiment WHERE id = 500000;`, against a table
with columns `id LONG, name STRING, random_double DOUBLE`.

We will use the median time of five queries per partition size, including the
first query, with minimum–maximum spread. Each size has a separate setup JVM
for CREATE and COPY, followed by one fresh measurement JVM executing five
identical SELECTs. There are no additional warm-up queries. Repetition 1 is
the **first query**, and repetitions 2–5 are **subsequent queries**.
Filesystem-cache state is uncontrolled, and steady-state JVM warmth is not
guaranteed.

The timer starts immediately before SELECT binding and stops after operator
cleanup. It includes catalog loading, planning, pruning, execution, and normal
DEBUG logging. Parsing, JVM startup, ingestion, CSV output, and writing the
timing summary itself are excluded. At partition size 2, each SELECT considers
and logs 500,000 partition decisions. The measurement is an elapsed duration,
not a CPU-time or isolated storage-I/O measurement.

The fixed heap is `-Xms2g -Xmx2g`. Generate data using `random.Random(67)`:
for each increasing ID, draw a name from `Slava`, `Vasya`, `Anton`, `Taras`
using `rng.choice`, then draw `random_double` using `rng.random()`. All sizes
reuse one headerless CSV. Run sizes in ascending order, with fresh storage
and logs for each size. The detailed protocol is in `Detailed-Experiment-Plan.md`.

##### Example Data

id, name, random_double
1, Slava, 2.2
2, Vasya, 3.2
3, Anton, 3.3
4, Taras, 3.6

##### Example Query

`SELECT * FROM experiment WHERE id = 500000;`

### Hypothesis

"It looks like a parabola. There will be a valley where no larger partition size and no smaller partition size will decrease the time".

Evaluate this hypothesis from the measurements; do not force a curve shape.

### Reproducing the experiment

Use Python 3.9 or later, with Matplotlib available for chart generation.
The generator, runner, extraction and statistics use only the standard library.

```bash
python3 -m unittest discover -s scripts -p 'test_*.py'
mvn verify
mvn package
python3 scripts/partition_experiment.py smoke-run /private/tmp/boomdb-smoke-new --resources-confirmed
python3 scripts/partition_experiment.py full-run /private/tmp/boomdb-full-new --resources-confirmed
python3 scripts/partition_experiment.py chart /private/tmp/boomdb-full-new
```

Pass `--resources-confirmed` only after checking that the fixed heap and
filesystem workload are feasible. The runner checks free disk space and that
the launcher JVM accepts the heap. Directory names must be new: existing runs
are never overwritten or resumed with replacement samples. The independent
`generate <csv-path>` command generates the full dataset without running queries.

Each run preserves the exact source files (including untracked files), source
commit and uncommitted patch, packaged JAR, checksums, conditions manifest,
dataset, SQL scripts, stdout/stderr, all rotated logs, raw and summary CSVs,
and PNG/PDF charts. Raw rows label first versus subsequent queries. Machine
model and total RAM may require a separate user-supplied record if machine
statistics cannot be read; the manifest must state that limitation explicitly.
The runner verifies the recorded JAR, launcher and logging configuration before
each invocation and stops if they change during the sweep. Run-directory paths
must not contain apostrophes, which the current SQL string grammar cannot escape.

The runner stops on failures, missing/duplicate samples, incorrect output,
or unexpected partition statistics. A full successful sweep contains exactly
90 samples over 18 sizes. Smoke results use 1,024 rows, target ID 512, and
partition sizes 2, 128 and 1,024, and remain separate from the full results.
